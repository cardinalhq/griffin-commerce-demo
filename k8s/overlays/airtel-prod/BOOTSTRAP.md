# Airtel Telemetry Demo — Bootstrap

Paste this into a fresh Claude Code session to continue work on the
Airtel managed-PostgreSQL-on-VMware demo.

---

## Goal

A live, operator-driven sales demo that shows Cardinal correlating an
application-level PostgreSQL SLO breach down through VMware
infrastructure (VM → ESXi host → shared datastore) and identifying the
blast radius across tenants — all from real OTLP metrics + logs landing
in lakerunner. Target customer: Airtel Cloud / Airtel Managed Services.

Source telemetry contract:
`~/Desktop/airtel_postgres_vmware_telemetry_spec.md` (3,191 lines —
metrics, logs, failure profiles, dashboard requirements, demo talk track).

## What's already built

1. **Simulator pod** in `griffin-commerce-demo/services/dbaas` (Go),
   shipped as the `dbaas` subcommand of the `griffin` binary, deployed
   to namespace `airtel-demo` in EKS cluster `prod-us-east-2-global`
   (account 992382549843). Emits OTLP metrics + OTLP logs for spec §4
   entities: 6 tenants, 1 vCenter, 2 clusters, 4 ESXi hosts, 3
   datastores, 6 VMs (incl. noisy neighbor), 4 PG instances. Metric
   names follow the spec exactly (`pg_*`, `vmware_*`, `node_*`,
   `tenant_slo_*`, `airtel_probe_*`, `cardinal_alert_active`).
2. **Four §29 failure profiles**: `vm_local_disk_saturation`,
   `vm_cpu_ready_contention`, `vm_memory_pressure_swap`,
   `datastore_latency_shared_infra` (the canonical demo). Trapezoid
   ramp (2-min up / plateau / 5-min down) with per-metric onset
   offsets that follow spec §28.2 timing (datastore → host → VM →
   Linux → PG → probe → SLO, with IndiGo joining as at-risk at +12min).
3. **Local HTTP fault server** on pod port 9999 — single-active-profile
   semantics. Endpoints: `POST /faults/activate?profile=<id>`,
   `POST /faults/clear`, `GET /faults/status`, `GET /faults/profiles`,
   `GET /healthz`. Reached via `kubectl port-forward`.
4. **K8s overlay**: `k8s/overlays/airtel-prod/`. Standalone (not based
   on the commerce-services base). Routes OTLP to the node-local
   collector daemonset `collector/aws-prod-us-east-2-global-agent` at
   `http://$(HOST_IP):4318`. **No Cardinal API key on the pod** — the
   collector handles upstream auth.
5. **Telemetry lands in the Cardinal HQ org**
   (`c4375e34-dfcf-498a-8ba3-a02d119baf82`), not Airtel
   (`3aa7b421-…`). The collector is wired to Cardinal HQ; until that
   changes, dashboards must live there too.
6. **Four maestro dashboards** in Cardinal HQ org — generated by
   `k8s/overlays/airtel-prod/dashboards/author.py` (stdlib Python,
   emits SQL). 24 + 26 + 28 + 15 = 93 panels across 37 sections.
   Idempotent: re-run to update.

## How to operate

```bash
# 1. Trigger a profile
kubectl -n airtel-demo port-forward svc/dbaas-faults 9999:9999 &
curl -sX POST 'localhost:9999/faults/activate?profile=datastore_latency_shared_infra' | jq

# 2. Re-deploy the simulator after code changes
#    (release flow: merge PR → tag vX.Y.Z → CI publishes to ghcr.io)
#    Bump newTag in k8s/overlays/airtel-prod/kustomization.yaml.
kubectl apply -k k8s/overlays/airtel-prod

# 3. Re-apply dashboards after editing author.py
kubectl -n cnpg-cardinal port-forward svc/cnpg-cardinal-rw 15432:5432 &
python3 k8s/overlays/airtel-prod/dashboards/author.py > /tmp/airtel.sql
PASS=$(kubectl -n maestro get secret pg-credentials -o jsonpath='{.data.MAESTRO_DB_PASSWORD}' | base64 -d)
PGPASSWORD="$PASS" /opt/homebrew/Cellar/libpq/18.4/bin/psql \
  -h localhost -p 15432 -U maestro -d maestro -f /tmp/airtel.sql
```

## What's still loose / fragile

- The Airtel org is empty — telemetry routing to it would be a
  collector-config change in `kubernetes-clusters/prod/collector/…`.
- The MCP system API key's user id `system:mcp-api-key` isn't a UUID,
  so `POST /api/orgs/:orgId/dashboards` 500s on the `created_by`
  insert. Workaround: direct PG insert with NULL `created_by`. A
  cleaner fix is a maestro patch that nulls out non-UUID user ids
  before the dashboard insert.
- Dashboard PromQL needs `last_over_time(metric[5m])` + `or on()
  vector(0)` patterns for KPI tiles — otherwise zero-match renders
  "No data" and sparse samples drop entries from counts.
- The Cardinal HQ org's "DBaaS — Tenant View" dashboard is the *old*
  griffin-commerce-demo dbaas — it queries `db.*` metrics that aren't
  emitted anymore. Either delete it or rewrite it.

## Anchored decisions (re-confirm before changing)

- **Single in-place service**, not a sibling. `services/dbaas` was
  repurposed; the HDFC commerce demo tenants were retired.
- **Node-local collector**, not Cardinal API key on the pod. Mirrors
  the `griffin-demo` namespace pattern.
- **Direct PG insert for dashboards**, not REST. Workaround for the
  UUID/createdBy quirk. Reapply is one-shot idempotent SQL.
- **Cardinal HQ org**, not Airtel, for now. Move when the collector is
  re-routed.
- **Four profiles**, single-active semantics. Replacing semantics on
  re-activate. 35-min duration with trapezoid ramp.
- **Spec §28.2 temporal order**: encode all incident metrics with
  `OnsetOffsetMin` per spec — don't shortcut.
- **`SERVICE_NAME=dbaas` on the container**, not `args:[dbaas]`. The
  entrypoint dispatches by env var.
